# FalsifyAI M1: parser and critic

M1 operationalizes a hypothesis and then attacks the resulting claims. It does not try to prove the hypothesis, and it does not build a null model, an observable plan, a simulation, an experiment, or a verdict.

Two routes are available. Neither route runs the other one for you.

| Method | Path | Default |
| --- | --- | --- |
| POST | `/api/v1/analyze/parse` | `mode=stub` |
| POST | `/api/v1/analyze/critique` | `mode=stub` |

`mode=stub` uses deterministic fixtures and does not open a network connection. `mode=live` calls `POST {META_BASE_URL}/chat/completions` on Muse Spark with a JSON schema. Live mode does not fall back to the stub. A missing `MODEL_API_KEY`, a missing `META_MODEL_ID`, or an invalid `META_BASE_URL` returns HTTP 503. A live response that does not match the schema, or that adds a number or a source the user did not write, returns HTTP 502.

The verified model id is `muse-spark-1.3`. The key is read from the environment and is not returned by these routes.

## Parse

Body: a `HypothesisInput` object (`statement` is required).

Response: a `ParserResult`.

```json
{
  "claims": [],
  "assumptions": [],
  "undefined_terms": [],
  "parser_notes": []
}
```

Each claim has `claim_id`, `statement`, `claim_type`, `variables`, `assumptions`, `is_operational`, `missing_definitions`, `provenance`, and `confidence`. `confidence` rates the extraction, not the truth of the claim. `provenance.origin` is `measured`, `literature-derived`, `assumed`, `simulated`, or `speculative`, under the same rules as `ScientificClaim`. A speculative claim has no source. A claim is operational only when its quantities are defined.

The parser keeps the smallest set of claims. It does not split one proposition into fragments. If a term is not a controlled, measured, or defined quantity, `is_operational` is false.

## Critique

Body:

```json
{
  "hypothesis": {},
  "parser_result": {}
}
```

Response: a `CritiqueReport` with `issues`, `blocking_issues`, `major_issues`, `minor_issues`, `conventional_explanations`, `required_clarifications`, and `summary`.

Severity is `blocking`, `major`, or `minor`. `blocking` is true only for blocking issues. `affected_claim_ids` must refer to claims in the supplied parser result. Categories are used only when they apply. They include undefined variables, dimensional inconsistency, causal ambiguity, non-operational claims, hidden assumptions, parameter degeneracy, circular definitions, missing controls, conventional explanations, unsupported mechanisms, and non-discriminating predictions.

## Golden stub hypotheses

The stub recognizes three statements.

1. A measured pendulum period with a length, a unit, and a photogate. The claim is operational. The critic does not block it.
2. "Quantum biofield resonance improves systemic healing." The terms are undefined and the claim is not operational. The critic blocks it.
3. Tomato plants and a speaker, with vital energy offered as the mechanism. The critic records ordinary growth conditions as a conventional explanation and does not treat the mechanism as established.

Any other statement stays non-operational in stub mode. The stub does not add a measurement or a citation.

## Example

```powershell
uvicorn app.main:app --app-dir backend --env-file .env --reload
```

```powershell
curl -X POST http://127.0.0.1:8000/api/v1/analyze/parse -H "Content-Type: application/json" -d "{\"statement\":\"Quantum biofield resonance improves systemic healing.\"}"
```

Omit `mode` for the stub. Add `?mode=live` only when the process environment has the key, the model id, and an https base URL.
